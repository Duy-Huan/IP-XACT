## What CHIA actually provides

CHIA means Co-designing Hardware/software with Intelligent Agents (page 2,
footnote 1). Its main abstraction is a **workflow** consisting of a loop and a
cluster. A loop is a directed cyclic task graph, with programmatic and agentic
control/data edges; workers advertise resources and the Ray runtime schedules
functions to eligible workers (sections 3–4, pages 3–7). ChiaFunction.py corroborates
local/remote function calls, Ray resource options and cache/bypass dispatch.

The paper describes reusable nodes for Chipyard/CIRCT, Verilator, FireSim, gem5,
ChampSim, Spike/torture and Hammer, plus agents, storage and profiling. These are
workflow/evaluation tools, not an automatic behavioral implementation for every
SoC or every IP described in XML. In section 5.2 (page 9), the user must supply
an ISA golden reference and instruction collateral. The paper does not establish
universal SoC construction or industry signoff. The reviewed paper/source do not
present the IP-XACT-2022-to-canonical-SoC-IR contract that this project targets.
Current source also contains ESP/SystemC-HLS references; those references must
not be misrepresented as the same unified QEMU/gem5/SystemC execution path.

Container isolation, runtime profiling, retry/rescheduling and caching are first-
class features (pages 4, 6–7). The page-4 isolation discussion explicitly assumes
non-adversarial but potentially unreliable LLMs; it does not claim to contain
malicious agents. The current cache code writes results by user-supplied tags and
uses explicit bypass for replay. A replay or supplied node output must be labelled
as such, not presented as a new simulation measurement.

## Reported measurements and their limits

All numbers below are **author-reported**, not measurements reproduced here.

| Evidence in the provided v3 PDF | Meaning and boundary |
|---|---|
| MediumBOOM → gem5 alignment, section 5.1, page 8 / figures 4–6 | 202 iterations over about 10.5 days; 36 training microbenchmarks; best training average cycle-count difference 2.80%; holdout figure reports a best 6.12% |
| Alignment discussion, pages 8–9 | Agent cannot see Embench holdout sources/results. Authors identify outliers and a benchmark-tuned penalty-suppression parameter causing overfitting. These numbers do not establish accuracy for arbitrary workloads or SoCs |
| ISA extension verification, section 5.2, pages 9–11 | Spike co-simulation, base ISA tests and random riscv-dv programs precede long workloads; Bitmanip/Zicond evaluations execute 25.5 trillion SPEC06 reference instructions in FireSim on a Chipyard/BOOM SoC; Crypto uses OpenSSL |
| Timing/IPC optimization, section 5.3, page 12 | About 2.03× Sky130 synthesis frequency, 3.28% SPEC06 IPC loss, reported net speedup about 1.97×; evaluated on the selected MegaBOOM design |
| Technology transfer caveat, page 12 and section 7/page 17 | Most Sky130 optimization gains did not generalize to the advanced commercial process beyond the first optimization. Public-PDK QoR is not a universal predictor for another process |
| Case-study conclusions, page 17 | Examples are illustrative rather than exhaustive; fast high-fidelity evaluation and verification remain bottlenecks |

The key lesson is independent, workload-representative validation. A native IPC
counter or a high pass count does not substitute for correlation against a golden
implementation. Simulating and synthesizing with multiple tools must be followed
by explicit agreement checks; sharing a workflow does not itself make timing or
hardware semantics agree.

## Direct comparison

| Dimension | CHIA paper / inspected source | This platform, independently checked |
|---|---|---|
| Primary abstraction | Agentic/programmatic workflow graph plus resource cluster | IP-XACT importer, typed SoC IR, model contracts and scoped backend execution |
| Composition | Reusable task nodes for building/running/evaluating tools; user supplies design, configurations and verification collateral | Real cross-engine/SystemC integration for supported 7/8/9-role profiles; arbitrary instance/bus graphs not executable yet |
| CPU/RTL scale | Paper demonstrates BOOM/Chipyard, Spike validation, FireSim and long workloads | Accepted Ibex/normalized RV32 RTL profiles; Rocket request fails without an adapter |
| Timing trust | Selected RTL↔gem5 alignment with training/holdout measurements and documented outliers | Native gem5/RTL counters, but no target-wide correlation/error budget or held-out calibration result |
| Functional oracle | Section 5.2 isolates implementation agents from verification infrastructure and requires user golden models | Negative/native tests and source/artifact hashes; no comparable independent held-out qualification campaign demonstrated |
| Execution scale | Ray scheduling, heterogeneous workers, profiling and distributed failure recovery | Local bounded subprocess orchestration and caches; no demonstrated distributed resource scheduler |
| Physical evidence | Hammer-backed selected synthesis/QoR studies, public/commercial technology caveats | Separate public-library nine-component reference layouts/mapped firmware; full inventories and industrial closure remain open |

These are complementary layers. CHIA could orchestrate this compiler/runner as
nodes, but that integration is **proposed, not implemented or tested**. Adding
CHIA would not provide missing IP models, AXI/TileLink/MMU adapters, generic IR
lowering or target-calibrated timing automatically. CHIA's README specifies Python
3.10.19 for its container environment; this SDK uses Python 3.12.14. Preserve
separate versioned environments until compatibility is actually verified. Native
Podman compatibility with CHIA's Docker-oriented cluster setup was not tested.

## Recommended development gates

1. Generalize the existing compiler first: instance identity must be independent
   of model role; support multiple existing IP instances, typed bus/IRQ/clock/reset
   graphs and visibility/translation checks. An unseen two-UART/two-GCD design
   should execute without inventing another hard-coded board profile.
2. Qualify one actual CPU/bus/OS path, including reset, exceptions, MMU and Linux
   where requested, instead of relabelling a native ISS as the requested RTL CPU.
3. Adopt the CHIA-style validation discipline: immutable/isolated golden models,
   separate training and holdout workloads, per-workload cycle error, performance
   counters and traces, and technology-specific PPA constraints. Reject regressions
   and preserve all failed/blocked evidence.
4. Then evaluate an explicit CHIA wrapper around compiler/build/simulation/
   verification/QoR nodes. Retain input/build hashes and reject stale or bypassed
   evidence at acceptance. Resource/disk budgets, retry policy and profiling belong
   to this orchestration layer; passing nodes is not full-SoC completion.

The current project is a controlled pilot/prototype for supported configurations.
It is not yet a general industrial platform for arbitrary SoCs. Fresh full-scope
requests for AI_SOC and AIZ_SOC both returned BLOCKED with exit code 1 and
full_system_complete=false while their selected independent stages passed.
See docs/industrial-readiness.md and the retained assessment run bundles.
